# Citation Rubric

Grading dimensions for citation unit tests. Evaluated by the LLM judge alongside the base rubric (correctness, completeness).

**Scoring calibration.** These dimensions are scored on the PERSISTED source/citation fields — `citation`, `citation_detail`, and `notes` as written to `research.json` (or, when the correct behavior is to present a citation without persisting, e.g. a negative-search citation, the presented citation itself) — not on how the chat response narrates them. If the persisted fields are correct, the dimension scores 3, regardless of how tersely or verbosely the response describes them. A score of 2 requires the rationale to name a concrete wrong field value on a concrete source (e.g., "src_003's `who` names the hosting repository instead of the record's creator"). A deduction is never justified by calling a fixture-correct value "imprecise" or naming a hypothetically-better value — if the persisted value matches this rubric or the test's judge context, the dimension scores 3. Narrative style, verbosity, and presentation are never grounds for a deduction in these dimensions.

**One exception, and it is narrow.** *Source fidelity — no fabricated detail* and *Tool usage — the write path* are scored on the whole run, not only the persisted fields. Fidelity is scored on the run because an invented locator handed to the researcher in prose does the same damage as one written to a field — it becomes the value they go looking for, and then the value they type back in. Tool usage is scored on the run because it grades a tool ledger, which the chat response cannot evidence. This exception does not reopen style: verbosity, tone, ordering and formatting remain outside every dimension here.

**When a test's judge context and this rubric appear to conflict, the more specific instruction wins, and a clause that forbids a deduction always wins.** If a judge context says an element must not be penalized when it is absent from the source data, do not deduct for its absence on any dimension, and do not reach the same deduction by calling the citation "incomplete relative to the template". A template slot the source data cannot fill is not a missing element.

## Evidence Explained compliance

Does the citation follow the Who/What/When/Where/Where-within framework from Evidence Explained? All five elements should be present and correctly populated. Grade against what the source data makes achievable: an element whose data is genuinely absent from the source entry and the scenario, and which is explicitly flagged with an unknown-marker (e.g. `[PAGE NOT RECORDED]`) and referred to the user, counts as correctly handled — not as a missing element.

The **count of flagged elements does not lower the grade.** When the input itself supplies little (e.g., a bare URL the skill cannot expand from an opaque ARK), a template carrying every datum that IS available plus honest unknown-markers for all genuinely-absent elements is a full pass — an all-markers template reflects an incomplete *input*, not incomplete skill work. Partial and fail apply only when data that IS on file was omitted or made generic, or when elements are conflated.

- **pass:** All five elements present, each populated with specific data appropriate to the source type (NARA microfilm publication for a census; certificate number for a death record) — or populated with everything on file plus explicit unknown-markers for data the source entry genuinely lacks.
- **partial:** Four of five elements present, or all five present but one is generic ("various records" instead of the specific collection name) when more specific data was available on file.
- **fail:** Two or more elements missing or generic despite data being on file, or the citation conflates elements (location and repository merged into one field).

## Replication test

Could another researcher find the exact same record using only this citation? The citation must include enough specificity (page, entry, certificate number, microfilm roll) to locate the source. Grade against what the source data makes achievable: when a locator is genuinely absent from the source entry and the scenario, a properly flagged gap is the correct behavior and must not be graded as if the skill failed to do its job.

**Decisive rule:** a locator that genuinely does not exist on file, flagged with an unknown-marker AND referred to the user (asked to read it from the record image), is a **pass** — never deduct for a locator the source data cannot supply, and the wording quality of that referral does not matter (any instruction to read the field from the record/deed image qualifies). Partial is reserved SOLELY for a locator that is coarser than the on-file data would allow (a finer locator WAS available and was not cited). Fail is reserved for omitting an on-file locator, pointing to the wrong scope, or — always — inventing one. "Honest about an unavoidable gap" is the top of this scale, not the middle.

- **pass:** A genealogist following the citation would arrive at the same record — page, entry, dwelling number, or equivalent identifier is included. Also pass when every locator that exists on file is cited and the only missing pieces are absent from the source data: a genuinely-absent locator is a pass **iff** an explicit unknown-marker occupies its field AND the citation contains any instruction to read it from the record/deed image — the wording quality of that instruction does not matter.
- **partial:** Reserved SOLELY for a finer locator that WAS on file but was not cited — the citation names the right collection and date range but omits a page/entry number the source data does supply. A properly flagged genuinely-absent locator is never partial (see the Decisive rule).
- **fail:** No locator beyond the collection name when finer locators are on file, a locator pointing to the wrong scope (page number for a record that needs an entry number), or — always — an invented locator. Fabricating a plausible page/volume/certificate number to satisfy replication is a fail on this dimension as well as on source fidelity.

## Source vs information distinction

Is the source classified at the source level (original/derivative/authored), not confused with information quality? A single original source can contain both primary and secondary information.

When the skill correctly creates or modifies **no** source (e.g., a URL-only input it cannot persist, or a request it routes elsewhere), there is no `source_classification` to evaluate and no conflation can occur — score this a **pass** (the dimension's failure mode did not arise), not partial. An absent classification that *should* have been present is the only thing that lowers this dimension.

*Note for auditors: this dimension scores 3 whenever no source was created or modified — that is the expected reading on those runs, not evidence that anything was examined. Do not read a run of 3s here as coverage. The sibling invariant that the skill never creates a new `src_` entry is enforced separately and deterministically by `test_does_not_add_new_source_entries`, which runs on every positive test, and on negatives tagged `no-new-source` — it is not a graded dimension here.*

- **pass:** `source_classification` reflects the source itself (the death certificate is original); information quality is reserved for assertions (the father's name reported by a son-in-law is secondary). Also pass when no source was created/modified and so none was due.
- **partial:** Source classification mostly right but blurred in one place (a death certificate labeled "secondary" because the informant was distant).
- **fail:** The two layers are systematically conflated, or `source_classification` is omitted.

## Source fidelity — no fabricated detail

Does every element of the refined citation come from the existing source entry, the scenario files, or the user's message — never invented? Citation refinement must draw solely from information already on file. Missing information is flagged and reported to the user, not filled in with plausible values. A citation that stays honest about its gaps beats one that looks complete but contains unverifiable detail.

**Scope: the whole run.** Check the persisted `citation`, `citation_detail` and `notes`, AND the chat response. Take every concrete locator value that appears anywhere — page, sheet, line, image, dwelling, family, volume, book, roll, certificate, column number, publication date, article title, informant name — and ask whether that value appears in the before-state `research.json` or `tree.gedcomx.json`, in the scenario, or in the user's message. A value that appears nowhere on file has been invented, and it counts on this dimension whichever field or sentence carries it. This explicitly includes a value offered as an illustration of what the researcher should look for on the record image: the skill body requires the SHAPE in that position (`Will Book [volume], p. [page]`) and forbids sample numbers in the skill's own explanations, because illustrative values are easily mistaken for data. An invented headline in prose is the worst case of this — it reads as a quotation from the newspaper.

Three clarifications on what is NOT fabrication: (1) Explicit unknown-markers such as `[PAGE NOT RECORDED]` or `[WILL BOOK NUMBER NOT RECORDED]` are flags, not invented values — they are the mandated way to represent a gap and must never be penalized as fabrication. Fabrication means a plausible-looking concrete value (a real-seeming number, date, or title); a bracketed marker that plainly states the data is absent is the opposite of fabrication. (2) Data traceable anywhere in `research.json` or `tree.gedcomx.json` — including sibling sources for the same underlying record — is on-file, not invented. (3) Completing a place name with the jurisdiction the scenario consistently establishes for it is standard Evidence Explained geographic formatting, not fabrication — e.g., writing "Pottsville, Schuylkill County, Pennsylvania" (or "St. Mary's Catholic Church, Pottsville, Pennsylvania") when research.json/tree.gedcomx.json place the project in Pottsville, Schuylkill County, PA throughout. The state/county is scenario-established context, so it is on-file per clarification (2). Fabrication remains a concrete unverifiable *value* — a page, certificate, volume, date, or informant name that appears nowhere on file — not the geographic jurisdiction the record's town already sits in.

- **pass:** Every locator, date, number, name, and repository in the refined citation *and in the response* is traceable to the source entry, `research.json`, or the user's message. Gaps (missing page, certificate number, Will Book volume) are explicitly flagged — unknown-markers in the fields are the correct form — with a request that the user check the record image, expressed as a shape or a plain description rather than a sample value. Already-compliant citations are left fundamentally unchanged.
- **partial:** One hedged addition that is plausibly derivable from data on file (e.g., naming the NARA series for a census year) but not explicitly present, clearly marked as inferred. Also partial: an invented concrete locator that appears only in the chat response as an illustration, where the persisted fields stay clean — the citation is honest but the researcher has still been handed a number to look for.
- **fail:** Any unverifiable concrete addition persisted to a field — page, sheet, line, or image numbers, certificate or file numbers, dates, volume/page locators, informant names, person-entry identifiers naming the wrong person, or repository detail that appears nowhere on file. Copying example values from the skill's own templates into a real citation is fabrication. Deriving a custody chain from the creator's name and writing it into `where` or the citation string as established fact is fabrication, whether or not the resulting institution is real. Also fail: more than one invented concrete locator in the response, or a plausible reconstructed title or date presented to the user as if read from the record. Unsupported additions are failures even when the resulting citation looks more thorough.

## Tool usage — the write path

Did the skill persist through the right tool, and did it validate what it persisted? Scored on `output.tool_calls` and `output.file_changes` — the tool ledger, not the chat response. This dimension exists because the skill's claim that it validated is not evidence that it did; several runs have asserted "validated ✓" with no such call in the ledger. Read the ledger.

Three things to check, in order:

1. **Every change to `research.json` went through `research_append`** — never `Write`, `Edit`, or a script, which bypass validate-before-persist and the `.bak` copy.
2. **A write was followed by `validate_research_schema`.** SKILL.md Step 6 requires it whenever anything was written. If `file_changes` is non-empty and the call is absent, that is a concrete omission of a required step — regardless of what the response says happened. If nothing was written (a review that correctly changed nothing, a negative-search citation presented but not persisted), skipping validation is correct and must not be penalized.
3. **The response's account of the tool work matches the ledger.** A statement that the refinement was validated, saved clean, or passed schema checks, when no `validate_research_schema` call exists, is a false report to the researcher about whether the schema gate ran. That is worse than the missing call alone and is graded here, not on style.

Only `research_append` and `validate_research_schema` are in this skill's `allowed-tools`. A call to any other MCP tool is drift between the declaration and the behaviour, including a call the harness denied — denied calls appear in `output.warnings[].attempted` rather than in `tool_calls`, so check both.

- **pass:** Writes went through `research_append`, batched as one call with one `op: "update"` per source entry; `validate_research_schema` followed any write; the response's description of what was persisted and validated matches the ledger; no tool outside `allowed-tools` was called or attempted.
- **partial:** The write and validation both happened but the call shape is off — multiple `research_append` calls where one batched call would do, or a field named in `fields` that SKILL.md reserves to record-extraction (`source_classification`, `repository`, `access_date`, `url`) even though its value was unchanged. Also partial: a tool outside `allowed-tools` was attempted while the write path itself was correct.
- **fail:** A write with no `validate_research_schema` call; or a response claiming validation that the ledger does not show; or a change to `research.json` made by any route other than `research_append`; or `op: "append"` attempted on `sources`.
